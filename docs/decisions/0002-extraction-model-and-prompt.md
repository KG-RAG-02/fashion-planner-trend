# 0002 기사마다 구조화 출력 1회, 프롬프트와 모델 기준선 고정

- **상태:** 채택 (2026-11)

## 배경
기사를 Style, Item, 속성으로 바꾸고 정확한 근거 인용을 붙여야 한다. 출력은 그래프로 들어가므로 기계가 검증할
수 있고 다시 돌려도 같아야 한다.

## 결정
- 기사마다 OpenAI API를 한 번 부르고, Pydantic 모델에서 만든 엄격한 JSON 스키마로 출력을 받는다. 그 뒤 코드로
  후처리와 검증을 하고, 실패하면 오류 목록을 붙여 최대 한 번 다시 시도한다([extraction.md](../extraction.md)).
- 프롬프트는 파일 하나 `prompts/article_extraction.md`이고, 식별자 `article-extraction`와 실제로 보낸 본문의 SHA-256으로
  구분한다. 프롬프트의 예시는 모두 합성이다.
- 모델은 코드가 아니라 설정(`LLM_MODEL`)으로 정한다. 작성자들의 그래프를 만든 기준선은 `gpt-6-sol`, 추론 강도
  `none`이다.

## 프롬프트가 지금 모양이 되기까지
공개 레포에는 마지막 프롬프트만 남겼다. 그 전 단계는 다음과 같았다.

1. 첫 프롬프트로 추출기, 검증기, 일괄 실행 스크립트를 만들었다.
2. 개발용 기사 8건의 결과를 보고 "트렌드의 예로 든 옷만 Item", "트렌드의 하위 갈래를 Style로 나누지 않는다",
   "일반 서술·다른 맥락의 옷·총칭은 뺀다"를 명시했다. 이 판이 한동안 스크립트 기본값으로 동결됐다.
3. 기사 앞머리에 시즌 후보(값, 출처, 횟수)를 넣고 시즌 규칙을 구체화했다. 이때 예시에 쓰던 실제 기사의 트렌드명과
   인용을 합성 예시로 모두 바꿨다.
4. Item 판정을 일부러 넓힌 실험판("애매하면 Item")을 만들었다. 같은 작은 모델에서 라벨과 일치한 Item은 크게
   늘었지만(개발용 5건에서 6 → 18), 라벨에 없는 Style을 만드는 오류도 생겼다(0 → 5).
5. 라벨링 기준을 반영한 지금 판: 정의는 한 문장, 설명은 항목 하나에 사실 하나, Style 근거는 정의의 모든 주장과
   각 시즌을 받친다, Item은 넣는 기준 2가지와 빼는 기준 6가지로 판정하고 애매하면 내지 않는다, 성질만 말한
   소재는 원문 표현만 둔다, 핵심 속성은 6개 속성에서만 고른다. 함께 코드에 이름 앞 표지어 제거(P2)와 자리표시자
   이름 검사(V1)를 넣었다.

## 결과
- 검증이 지어낸 인용, 가리킨 블록에 없는 원문 값, 있을 수 없는 이미지 연결을 잡는다. 실패한 기사는 그래프 대신
  검토 폴더로 간다.
- 추출을 실행하면 기사 텍스트가 OpenAI로 가고 비용이 든다(작성자들의 193건 실행은 약 USD 4.6). 응답은 로컬에
  캐시되므로 다시 돌리면 비용 없이 같은 결과가 나온다.

## 근거와 그 한계
사람이 라벨을 단 개발용 기사 5건에서 기준선은 라벨 Item 39개 중 33개를 찾고 6개를 놓쳤으며 3개를 잘못 만들었다.
직전 후보 모델은 31 / 8 / 8이었고 비용은 비슷했다. 라벨이 있는 23건 전체에서는 라벨 Style 31개 중 30개를 찾았다.
모두 프롬프트를 만드는 동안 고른 작은 표본이고 원 실험 파일은 공개하지 않으므로, 벤치마크가 아니라 상식 점검
수준으로 읽어야 한다.

## 검토한 대안
- 기사마다 여러 번 호출(Style 먼저, 그다음 Item): 비용과 실패 지점이 늘고, 한 번 호출 결과가 검증을 통과한 뒤로는
  필요 없었다.
- 로컬 CLI 에이전트 백엔드: 재현이 어려워 뺐다([troubleshooting.md](../troubleshooting.md)의 T-LLM-02).
